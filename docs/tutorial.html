DMTL Tutorial

DMTL is a language for building custom reports, inspired significantly by the Haskell programming language (along with some related research). Like Haskell, it is a functional language, and programs are constructed by giving a series of definitions of types and values. The values in the language are immutable, and variables cannot be reassigned; variables are simply names for a value (although names can be shadowed in local definitions). Also like Haskell, functions are first-class values in DMTL, and can be passed around like any other value.

DMTL also has built-in support for various relational algebra operations. It has types for database rows and entire relations, and functions for manipulating them.

Basic Syntax

A DMTL source file consists of a sequence of definitions, presented as equations. For instance:

m = 5

defines the variable m to be bound to the value 5. Normal identifiers must start with an alphabetic character and may continue with alphanumeric characters, ' and _. Functions may also be specified in this manner, by giving a sequence of argument identifiers like so:

const x y = x

This definition form mirrors the use of functions; if f is a function, and x is a value of the appropriate type, then f x denotes the result of f when fed the value x. Parentheses are necessary only for grouping. Function application is left-associative, so f x y z is equivalent to ((f x) y) z. DMTL also has function literals, traditionally known as lambda expressions, for when a function is needed in-line and isn't worth giving a name. For instance, the definition:

konst = x y -> x

is equivalent to the previous definition, and uses a function literal on the right hand side instead of a parameter list on the left.

Definitions may also be accompanied by an optional type specification, consisting of the name followed by a colon followed by the type:

n : Int
n = 5

id'int : Int -> Int
id'int x = x

The second definition is given the type of functions from Int to Int. The -> operator is right associative, meaning that T -> U -> V is equivalent to T -> (U -> V). This matches appropriately with the left associative application like so:

f : A -> B -> C -> D -> Z
f a b c d = ...

Definitions may refer to the name being defined, allowing for recursive definitions:

factorial : Int -> Int
factorial n = if (n == 0) 1 (n * factorial (n - 1))

And like Haskell, infinite structures may be constructed by recursion, and are lazily evaluated.

ones : List Int
ones = 1 :: ones

where :: constructs a list from a head element and a tail list.

Comments are currently limited to a single line, and are introduced by two dashes:

some code -- this is a comment

Types

Standard Types

DMTL has a number of primitive, specially handled or just predefined types.

  • Int

    This is the type of machine-length integers. Integer literals have this type, and there are basic arithmetic functions defined for them.

  • String

    This is the type of character strings. String literals are delimited by double quotes, and there are a few primitive functions for working with strings.

  • Double

    This is the usual type of double-precision floating point numbers. There are as yet no literals for Double, but they can be produced by using mkDouble with a string.

  • List

    Lists are not technically a primitive type, but they receive special handling. [] denotes an empty list, while h :: t builds a list out of a head element h and a tail list t. There is also special syntax for defining a list with several given elements:

    [1] : List Int
[1, 2] : List Int
[1, 2, 3] : List Int
...

  • Bool

    Bools are not primitive either, but they are defined in the default prelude. They have constructors True and False, and can be branched on using the if function (or the bool function, which takes the boolean condition last, if that's more convenient). Due to DMTL's lazy evaluation, if is just a regular function; no special forms are necessary to delay the evaluation of the branches.

  • List#, Maybe#, Pair#, Function1, Function2, ...

    These are imports of corresponding Scala types. There are conversions between similar DMTL types and these, for interoperation.

    listIn  : List# a -> List a
listOut : List a -> List# a

toFn2 : (a -> b -> c) -> Function2 a b c

These are mainly used for interoperation with imported Scala code. For instance, the report writers are defined in Scala, imported into DMTL using these primitive functions, and then wrappers are written to give them more sensible DMTL types.

Algebraic Data Types

DMTL is not limited to the predefined types above; new types can be introduced using the data keyword. These declaration allow one to define types by giving a series of constructors by which it can be built. Each constructor is a name followed by a series of types indicating the fields it should contain, and the constructors for each data type should be separated by |. For instance, the type of booleans above is just an ordinary data type:

data Bool = False | True

Data types may also be parameterized by one or more types by giving a list of variables, similar to the definition of a function. For instance:

data Maybe a = Nothing | Just a

This defines an entire family of types; a Maybe Int is either Nothing or Just (n : Int), et cetera.

Finally, data types may refer to themselves on the right hand side of the definition, allowing one to create recursive types. For instance, the above-mentioned List is just:

data List a = Nil | (::) a (List a)

([] is sugar for Nil, and (::) is a way to write :: prefix.) So a List a is either an empty list or an element of type a prepended to another List a.

Finally, all data definitions of this type generate an eliminator, allowing one to do case analysis on the constructors, determining which constructor was used to generate a given value, and branching on the result. The eliminator is given the name of the type with the first letter down-cased. The following are the eliminators for the above types:

bool  : r -> r -> Bool -> r
maybe : r -> (a -> r) -> Maybe a -> r
list  : r -> (a -> List a -> r) -> List a -> r

In general, the eliminators have the following form:

  1. The eliminator takes a value of the data type to a value of a result type r, making the last bit T -> r, with T being the data type.
  2. For each constructor, there is one additional argument to the eliminator.
  3. The type of each extra argument is that of functions from all the fields of the particular constructor to the result type.
  4. The additional arguments to the eliminator appear in the order the constructors were specified in the definition.

So, for instance, the simplest eliminator would be for the 'empty' type:

data Empty -- no = is necessary when there are no constructors
empty : Empty -> r

Eliminators work by analyzing their last argument, and dispatching to the function corresponding to the constructor the analysis finds, so for instance:

bool x y False = x
bool x y True  = y

given the definition of Bool above. Also:

list z f Nil       = z
list z f (x :: xs) = f x xs

In the case of Empty, we have no constructors, so one can think of it being an empty set of cases. In practice, the only way to create a value of type Empty is with a vicious loop like so:

bad : Empty
bad = bad

empty will try to evaluate this value, and spin in an infinite loop, giving you a similar looping value of whichever r you have chosen to eliminate into.

Parametric Polymorphism

In the types of the eliminators above (and a couple other places), we made use of a variable r, intending it to mean that the eliminator works for every choice of type we wish to fill in for it. However, this was not just a convention of this tutorial; DMTL genuinely allows types containing variables, provided the definition is sufficiently oblivious to what that variable may be filled in with. For instance, a more general type for our identity function above is:

id : a -> a
id x = x

as it behaves exactly the same way regardless of the type of its argument. Another way of writing the same type is:

forall a. a -> a

explicitly quantifying the variable (DMTL will typically display types in this format). Further, DMTL is able to infer types of this format, so if we left the type annotation off, it would determine that id should have this type. Some other types of this form for above definitions are:

const, konst : forall a b. a -> b -> a
bad          : forall a. a
Nothing      : forall a. Maybe a
Just         : forall a. a -> Maybe a

Polymorphic functions like these are also first-class entities in DMTL, and can be passed around in functions. This feature is typically called higher-rank polymorphism. For instance, if we consider the following function:

f g = (g [1, 2, 3], g ['a', 'b', 'c'])

g is used with both a List Int and a List Char, so we need it to be capable of being used at multiple different types. This can be achieved by giving f the following signature:

f : forall r. (forall a. List a -> r) -> (r, r)

This says that g has the type forall a. List a -> r, and we can then instantiate a = Int in the first use and a = Char in the second.

Unfortunately, types of this sort cannot be inferred. If they are desired, specific annotations must be given to help DMTL determine what type you are expecting. The default mode of inference is to assume that all variables will be quantified outermost, fitting with the convention that a -> a is an abbreviation for forall a. a -> a, for instance, and not (forall a. a) -> (forall a. a).
